## Attribution defect: reproduced, with bounded corroboration

The collection repository was pinned at `9457f04a14cb2355ab00023420369d46ffd4a395` for this review. In [`preprocess.py`, lines 169–178](https://github.com/r-three/common-pile/blob/9457f04a14cb2355ab00023420369d46ffd4a395/sources/stackexchange/preprocess.py#L169), `process_revision` gets the supposed user ID from the revision's **Id**, instead of **UserId**. The later post-author construction looks that value up in the actual user-ID-to-display-name table (lines 415–423). It therefore associates a post with users whose IDs happen to equal its history-row IDs, or an empty set when no such user exists. This is a concrete code defect, not an inference from unfamiliar names.

An isolated execution of those actual pinned functions on a small synthetic XML record with revision ID 9001, post ID 14042, and user ID 42 returns `(14042, 9001)`, instead of `(14042, 42)`. Only `get_attr` and `process_revision` were extracted via AST; no collection program or model was executed. `provenance-checks.json` preserves the result.

Live Stack Exchange API checks of the first three shard questions found that question 14042's owner name and stable user ID 2195 are absent from its downloaded author list. The other two owners are present. The first three exclusive-4.0 questions also contain their owners. This does **not** validate their entire attribution: the collector separately adds comment authors using `UserId`, so an author who also comments can still appear correctly despite broken question/answer revision mapping. We did not audit all answer authors, revisions, editors, or commenters. These six checks are diagnostic and nonrandom, not a defect-rate estimate; live user names can change. Stable missing user identity is the stronger corroborating signal. API snapshots and comparisons are retained under `evidence/` and `live-owner-comparison.json`.

Across the complete local shard there are 55 empty author lists, including **43 among the 1,068 exclusive-4.0 rows**. Empty provenance is not repaired by the presence of a question URL.

The dataset card does not pin the collector commit that produced this dataset revision. Consequently this review does not claim proof that every downloaded row was generated by the inspected source version. The observed missing/empty attribution and the current collector's reproducible defect are enough to withhold admission; they do not establish an exact corpus-wide error rate.

`metadata.license` is the question's license, not a declaration that every component shares it. The collector's `all_licenses` aggregates question, answer and included-comment licenses (lines 280–287), and should be required to be exactly the permitted singleton for an exclusive-4.0 whole-thread intake. No top-level/per-component disagreement was found among the 1,068 exclusive-4.0 rows. This is a metadata consistency check, not proof that the contributing licenses or authors are correct.

[Stack Exchange's licensing documentation](https://stackoverflow.com/help/licensing) distinguishes versions by contribution date and directs readers to individual post revisions. A newer answer or a 4.0 question does not, by itself, make all older thread contributions 4.0. The repository README's statement that it considers only the question license describes the primary field; code supplies the additional aggregate list. Both must be interpreted accordingly.

[CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/) permits sharing and adaptation subject to its terms, including appropriate attribution, a license link, change notices and applicable ShareAlike obligations. The implementation should retain source and contributor identity, license information, revision/component provenance and transformation notices. The collection repository's MIT software license is not the license for its collected text. This review does not resolve legal questions about model weights or certify compliance for a particular downstream release.

## Flattening and extraction

The collector deliberately emits a single thread as title/question text, question comments, then answers and their comments, joined with newline separators. Answer ranking can prioritize the accepted answer and then vote score. The output lacks explicit question/answer/comment boundaries, per-component IDs, per-component author mappings, and per-component license fields; an unordered author set and license set cannot reconstruct those mappings. Paragraph breaks are not reliable role boundaries.

- Whole-thread text can be a useful candidate for broad prose, but it must not be presented as one author's continuous, internally consistent narrative or as a reviewed factual explanation.
- Distinct contributors can disagree, comments can reference missing images or external links, and extraction can discard HTML/link structure. Domain assignment and the fixed extraction-quality audit remain necessary. A site tag alone does not establish everyday, procedural, or explanatory coverage.
- Do not heuristically split the flattened string into “answers” to discard unapproved licenses or rebuild attribution. Correct component extraction requires structured upstream evidence. Keep whole-thread/source-family splits for leakage control.
