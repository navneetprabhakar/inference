SFT memory investigation — campaign stopped

Primary finding: the runner allowed MLX's freed-buffer cache to grow with variable sequence lengths. Default cache allowance was 22.8 GiB on this 24 GiB laptop. Existing telemetry recorded active tensor peak but omitted the cache. This is a runner memory-management defect; there is no evidence here of an unbounded retained-gradient graph.

Controlled local probes

Each process loaded the same 57,344-token checkpoint, optimizer state and data cursor. No concurrent GPU jobs. All updates discarded; all checkpoint hashes verified unchanged. Probes stopped at 8 GiB active-plus-cached allocation, 512 MiB new swap, critical thermal state, or 180 seconds.

Default variable-length batches crossed the diagnostic allocator ceiling within three seconds, before the first optimizer update. Active tensors were about 2 GiB while cached buffers reached 6.26 GiB. Clearing the cache released those buffers while active tensors stayed unchanged. The 256 MiB cap completed 40 updates (327,680 diagnostic input slots) across 275 sequence lengths. The fixed-length control completed 12 updates without runaway cache growth.

Cache may briefly exceed its configured limit: MLX reclaims it on subsequent allocations. Microbatch-end samples miss transient peaks; full active-peak counters are retained in events. Peak active allocation in the capped run was about 2.72 GiB.

Numerical check

Maximum absolute loss difference over the first 12 matching optimizer updates between capped trimmed inputs and fixed padded inputs: 0.00028089. Small differences are compatible with floating-point kernel differences; this is not a claim of bitwise equality.

What caused the previous stops

  • Sequential training can fill the allocator cache on its own; the concurrency explanation was incomplete.
  • Two GPU processes can each retain a large cache, so overlapping them amplified the risk.
  • The stale initial-swap baseline was a separate resume bug, already corrected. That correction did not address cache growth.
  • Post-exit system memory pressure and process RSS did not describe the peak GPU allocator footprint. Our initial diagnosis relied too heavily on those readings.

Recommended change, not yet applied

  1. Set mx.set_cache_limit(256 * 2**20) before allocations in both training and evaluation.
  2. Record active bytes, cache bytes, their sum, active peak, and session-relative swap growth.
  3. Keep sequential execution and current resource limits. Do not disable the swap guard to mask cache growth.
  4. Validate the corrected runner with a longer bounded run before extending the campaign. Keep the same data, optimizer schedule and 5M-token caps.

Production remains stopped at 57,344 tokens. A STOP file blocks accidental restart. No cloud use. The 129-second capped probe strongly supports the fix but does not prove multi-hour stability.

Primary references

MLX cache-limit documentation explains the default and reclamation timing. MLX cache-memory documentation distinguishes unused cached buffers from active memory. Local installed MLX version and docstrings were also inspected.
