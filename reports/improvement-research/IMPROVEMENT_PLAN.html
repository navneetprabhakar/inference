Improve the English conversation and tool-calling model

Research and local evidence reviewed 30 October 2026, IST. Planning only. Training remains stopped at 200M; no cloud/API spend authorized.

Recommendation: keep the existing 97.54M architecture and both base checkpoints. First separate decoding, missing supervision, and base-model capacity using a 2–3 day controlled experiment. Do not automatically resume generic pretraining to 300M. If the supervised experiments establish a useful learning signal but need more language capacity, continue a repaired, balanced pretraining recipe in gated increments toward 1B–2B total tokens. No credible evidence supports guaranteeing broad conversational quality on this laptop within a fixed short deadline.

1. Requirement and measurable acceptance

Confirmed: English text conversation, tool calls, strictly below 1B total parameters, random initialization, laptop-first, no cloud spending. Training must remain stopped until separately authorized. Battery training is allowed. Proposed v1 scope: short everyday conversation and context-grounded answers, five known read-only tools, clarification and short tool-result conversations. This narrow scope is a proposed first milestone, not a claim that you requested only a tool router. Broad open-domain knowledge, arbitrary new APIs, voice and long autonomous workflows have no defensible delivery ETA yet.

  • Strong evidence of learning, not readiness: the additional 100M tokens took 39,954 active seconds (11.10 hours), averaging 2,503 tokens/s. The model has seen only 2.05 training tokens per parameter. That ratio describes exposure, not a quality threshold.
  • Distribution shift: first-stage sampling was 80% web / 20% stories; continuation was approximately 50% web / 25% Wikipedia / 25% textbooks with no stories. Story regression is consistent with forgetting; it is not a controlled proof of the cause.
  • Missing post-training: zero conversation/tool supervised tokens. Role tokens exist in the vocabulary, but pretraining did not teach their protocol. Evaluations use literal User:/Assistant: prefixes. Chat failures do not isolate base capacity from missing instruction training.
  • Schedule confound: continuation increased learning rate from 3e-5 to 1e-4 and was stopped halfway through a schedule designed for 300M. Final LR at 200M was ~5.57e-5, not its intended 1e-5 endpoint. The checkpoint was not a fully cooled-down endpoint. Do not attribute every change solely to corpus quality.
  • Implementation evidence: causal masking, finite gradients, final partial-target masking, optimizer/checkpoint continuation and no-replay sampling have passed tests. FP32 generations reproduce the broad failures. These checks reduce specific bug hypotheses; they do not establish optimal initialization, LR, or document-boundary handling.

3. Repetition penalty: tested, not dismissed

Inference-only local experiment: both saved checkpoints, all 12 original prompts, greedy decoding, 96-token cap, sign-aware penalties applied once to previously generated token IDs, excluding prompt tokens. No weights changed. This is a small reused probe set, not a blind comparison.

Your point is supported: decoding improves repetition materially. At 200M and penalty 1.2, the greeting becomes “I’m a student. Assistant: I am a teacher. Assistant: I have to be a teacher.” It still loops. The weather tool request still repeats the question without JSON. The experiment does not establish an optimal penalty or show that stronger penalties cannot help.

Next decoding study: dev-only penalties {1.0, 1.1, 1.2, 1.3}, greedy and temperature 0.7/top-p 0.9, fixed three sampling seeds. Select on correctness, relevance and stopping as well as repetition, then freeze before the blind test. Compare learned EOS versus explicit next-role boundaries. Report outputs before and after boundary truncation. Test penalties separately for prose and JSON: repeated syntax, field names, numbers and copied facts can be necessary. Avoid treating a no-repeat-ngram ban as a default JSON policy. JSON-constrained decoding can improve syntax but cannot choose the correct tool or arguments.

References: Holtzman et al., decoding and degeneration; Transformers repetition-penalty definition. Local evidence: all 72 outputs, aggregate results.

6. Implementation and gated experiments

  1. Baseline and decoding, no training. Preserve 100M/200M weights and optimizer states. Expand development probes and run the decoding study. Verify tokenizer round-trip, role/EOS IDs, prompt formatting, teacher-forced versus free-running behavior and document boundaries. Current passing tests are retained. Do not insert untrained special tokens and interpret the resulting failure as a capability score.
  2. Build supervised pipeline. Native MLX, full-parameter tuning on checkpoint copies. Use existing role/tool token IDs and an explicit shared training/inference template. Mask system/user/tool-result labels; supervise assistant prose, assistant tool calls and turn-end token. Normalize loss by supervised target count and report full input tokens separately. Use one complete episode per padded sequence initially; avoid truncating answers/tool JSON or cross-example attention. The controller stops at an end token, validates a call, executes only an allowlisted local tool, appends its result and requests the answer. Reference semantics: assistant-only SFT loss; implement equivalently in MLX, do not switch frameworks just for the API.
  3. Small trainability check. After approval, overfit 64–128 checked episodes for at most 200 updates as a plumbing test. Require ≥95% training-set exact tool targets and correct stopping. This measures implementation/memorization only. If it fails, debug before larger runs.
  4. Four matched SFT arms. 100M and 200M bases × learning rates 1e-5 and 3e-5. Same examples/order/input budget, fresh SFT optimizer, 5% warmup and cosine decay to 1e-6, clipping and mixed precision. Cap each at 5M processed input tokens, including repeats/padding; four arms total 20M, not 20M assistant-target tokens. Evaluate at 1M, 3M, 5M. Tune decoding on development data only. SFT is expected to repeat examples; the earlier no-replay rule applies to pretraining, and epoch/exposure counts must be explicit.
  5. Decision gate. A promising arm must reach ≥60% dev conversation pass, ≥70% single-call execution, ≤10% no-tool false calls and ≥90% proper stopping, with no more than 10 percentage-point decline on its already-strong dev capabilities. These are continuation gates, not release gates. If 100M wins, use it; do not assume 200M is better. Validate the winner with a second seed (another ≤5M input tokens) before a long commitment. If neither passes but training targets are learned, quantify the generalization gap before prescribing more tokens.
  6. If SFT is promising: extend only the selected copy by 20M–40M supervised input tokens, with early stopping on held-out task success. Then run the locked acceptance suite and local runtime benchmark. If it meets the gates, package a narrow assistant. Keep raw, penalty-assisted and schema-constrained scores separate; any retry budget is reported independently.
  7. If the base remains limiting: authorize a controlled pretraining comparison first: two copies of the chosen base, 20M new tokens each, identical LR/schedule, original continuation mixture versus repaired mixture. Candidate repaired mix by tokens: 40% web, 20% Wiki, 15% textbooks, 15% new simple stories, 10% plain-English explanations. This is a hypothesis, not an established optimum. End both schedules with a deliberate cooldown; attach identical 5M-token SFT probes to both (50M total experiment exposure). Select by dev assistant/tool scores and held-out language loss, not lower perplexity alone. Require at least +10 percentage points in the failed primary capability, without >5-point regressions elsewhere; otherwise stop and reassess data/protocol/model capacity.
  8. Only if the repaired recipe wins: continue the selected base in bounded 100M–200M increments, first to 1B total, then optionally 2B. Preserve a 10%–20% simple-English retention share and fixed evaluation sets. Use an LR schedule tied to each approved endpoint rather than another blindly interrupted 300M schedule. At 500M/1B/2B, compare identical bounded SFT probes on copies. Stop if two consecutive increments fail to improve the deficient dev capability by ≥5 points, or regress protected capabilities by >5 points. Never expand automatically to 5B/10B.

Not first: a larger model, MoE/GQA rewrite, RL/DPO, huge synthetic-data campaign, or RAG to conceal basic instruction failures. A five-tool schema/controller and ordinary JSON validation are part of the proposed system, but an external LLM must not silently perform its reasoning. If reliable general conversation is mandatory, the laptop-only/random-weight constraint may need reconsideration; it cannot be fixed with an unsupported deadline.

7. ETA and resource budget

ETAs start after approval, not from this report. Measured 512-token pretraining speed: ~2,300–2,700 input tokens/s with checkpoint overhead; use the range, not the fastest burst. SFT is unbenchmarked: provision 1,200–2,500 processed input tokens/s until a 30-minute run measures padding/masking/context overhead. Host sleep and other workloads add time; charger removal itself no longer pauses training.

Cash: $0 cloud and $0 paid teacher APIs in this plan. Existing laptop, free admitted data and local fixtures only. 8. Approval boundary and artifacts

No training was performed for this research. The only new computation was 72 bounded inference outputs (~66.5 seconds). The 200M campaign remains awaiting review, and the 300M stage is blocked. Recommended next authorization is stages A–B only, capped at 20M SFT input tokens plus ≤200 smoke updates; a second seed, larger SFT or more pretraining requires the next decision.

Evidence: 200M full outputs and losses, 100M baseline, penalty outputs. All proposed metrics, mixtures and gates above are engineering choices informed by the cited research; they are not published guarantees for this custom model.
