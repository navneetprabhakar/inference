Decoding and conversation deep dive

31 October 2026. Offline inspection of existing results, code and frozen data; no new inference or training. Main remains the merged baseline. Recommendations below are proposed, not implemented.

Decision

Repair the measurement design before a decoding sweep. The current chat set primarily measures constraint-following, not everyday dialogue. Keep the selected V3 checkpoint frozen. Do not increase the global penalty or start another SFT run.

What the penalty sweep establishes

At 1.2, 64/100 chat outputs have at least one repeated token four-gram; at 1.3, 29; at 1.4, 10; at 1.5, 1. These are not human-rated unwanted-loop rates. Average output length falls from 70.27 to 63.98 tokens, and length stops fall from 21 to 12 cases. Repetition reduction therefore coincides with changed length and termination.

At 1.3 the paired tool comparison loses one single-call success and two chain successes, with no gains. At 1.5 it loses two single successes and twenty chain successes, with no gains. The 2-percentage-point development gate is an engineering rule, not a statistical significance claim; 2/75 chain cases is 2.67 points.

Actual argument corruption

Case v3-chain-599-v0: baseline second call multiplies a=735 by b=715; penalty 1.3 emits b=785. Final answers are respectively 525525 and 576975. The second answer is consistent with the wrong executed call, but the task fails. Case v3-chain-725-v0 changes add(-953,331) into add(-953,4), propagating the wrong result through conversion.

Actual prose improvement with residual failure

For the project-plan prompt, baseline repeats the literal phrase “highlighted section” throughout. Penalty 1.5 produces:

*The project plan should include *highlighted section*, which includes a clear and concise structure that aligns with the goals of your project.
*A successful project is crucial for ensuring it meets all requirements and objectives.

This reduces looping but does not give the requested three highlighted sections or a substantive list of project-plan features. These selected diagnostic examples are not a blinded quality rating.

Implementation hazards

  • The current penalty applies once to every unique generated token, including JSON numbers and syntax. It has no short history window and no distinction between prose and tool calls.
  • Current sampled decoding is fixed at temperature 0.7/top-p 0.9. Every generate call resets the same seed. Future runs need deterministic seeds derived from case, turn and replicate, avoiding identical random streams across turns.
  • The call parser accepts bare JSON as well as the call marker. A routing change must specify behavior for both, and count malformed/ambiguous outputs rather than silently repairing them.
  • The evaluator is given the expected number of calls and then asks for a final answer. It executes wrong valid calls correctly, but this remains a prescribed-step task harness. Add a separate protocol-driven rollout that follows actual emitted calls, with a fixed maximum step count, to measure autonomous stopping and tool choice. Do not silently replace the legacy score.
  • Choosing prose mode from record.kind would leak the task label. Use only actual offered tools, protocol state and emitted markers. In tool-enabled turns, retain the baseline selector until routing is established; test bare JSON, leading prose and mixed turns explicitly.
  • Four-gram blocking would mechanically improve our current four-gram metric. Measure independent longer loops, repeated sentences, instruction compliance and human quality; retain required repetitions.

Research assessment

  • Nucleus sampling: useful first inference ablation; it avoids deterministic maximization but cannot guarantee correctness or coherence in this undertrained model.
  • Contrastive search: balances likely candidates with hidden-state distinctiveness. Candidate evaluation adds compute and requires generator changes; defer until cheap alternatives are measured.
  • Unlikelihood and DITTO: training objectives can target unwanted token/sequence or sentence repetition. DITTO evidence concerns open-ended generation and summarization, not our tool model. If authorized later, compare against equal-budget normal SFT and preserve tool/replay supervision.
  • Critical min-p reanalysis: challenges claimed superiority after controlling evaluation and tuning. Do not expand the sampler search based on popularity or treat min-p as a proven upgrade.

Proposed bounded next phase

  1. Measurement repair (1–2 hours): freeze a small balanced development panel: 40 ordinary conversations, 40 short grounded/explanatory questions, 40 constraint tasks including required repetition, and 40 multi-turn/mixed-tool trajectories. Reserve separate source/scenario families for later confirmation. No model-generated reference answers. Define correctness and completion checks before outputs. Label old chat cases for repetition requirements and feasible answer budgets.
  2. Decoder and harness checks (2–3 hours): add explicit configuration, protocol-state routing, reproducible per-case/turn seeds, and logs for changed tokens, caps and stops. Tests must cover repeated JSON digits/keys, negative numbers, aliases, required quotations/repetition, EOS, malformed calls and identical baseline behavior on structured paths.
  3. Frozen-weight comparison (1–2 hours estimated laptop time): retain the old 96-token baseline, add a baseline with a 192-token ceiling where context permits, then compare three independent treatments at the matched ceiling: prose-only penalty 1.3; prose top-p 0.9/temperature 0.7 at three seeds; prose six-token repeat blocking as a diagnostic. Keep structural tool settings fixed. Do not combine treatments or tune a large grid. Exact time depends on longer outputs and current full-sequence recomputation.
  4. Review (1–2 hours): blind paired review of a preselected prompt-stratified subset; publish all outputs, seed ranges, paired win/loss counts, stop/length distributions, memory and latency. Compare automated strict fixture regressions on existing development cases, separately from the new runtime rollout.

Planning range: 5–9 hours including review, superseding the earlier 3–6-hour estimate because the data and harness audit revealed additional work. Laptop-only; no cloud/API costs. This estimate is not a live ETA and does not authorize training. Preparation can proceed without launching a model run.

Decision gates and next training decision

A candidate needs at least 50% fewer human-labelled unwanted loops, no material loss of task completeness or correctness in paired review, no more than the existing 2-point strict tool regression guard, and no hidden reliance on shorter answers. Report uncertainty by prompt/scenario family; correlated seeds are not independent cases. If no candidate passes, retain baseline. If outputs remain fluent but generic or wrong, further decoder tuning has reached its limit. Then propose a separate balanced-data SFT control versus targeted unlikelihood/DITTO experiment, with independently reviewed dialogue and fixed tool replay. No training is started now.
