# Post-optimizer language continuation: bounded proposal

Status: prospective technical proposal, 2026-11-06. No packing or GPU execution is authorized by this file. No current frozen runtime, queue, optimizer-screen criterion, or protected case is changed or opened. The user has authorized continuing toward a usable own-weight conversation/tool model; each next experiment still needs a concrete immutable specification and verified inputs.

## Purpose and limits

Test whether a simpler narrative/educational-web mixture improves language and context use in the existing 124,439,808-parameter random-initialization lineage. Nominal 60M targets is a bounded pilot, not evidence that this amount or a 50/50 mixture produces an assistant. There is no controlled comparison here that isolates mixture effects from additional training. Preserve baseline results and describe improvements as observed continuation effects.

The cleared partial candidate contains 31,495,666 narrative and 41,688,161 web training tokens, plus 629,749 narrative and 821,413 web validation tokens, according to the current preparation status. These are pre-packing counts, not final accepted targets. Custody clearance is not quality certification. Dialogue has only 237,187 eligible training tokens and 14 validation documents: exclude it from this pilot rather than manufacture a nominal 20M allocation by repetition. Narrative supplies simplified language; web limits abrupt narrowing of distribution. Equal proportions are an engineering hypothesis, not a demonstrated optimum or a literature prescription.

## Position exposure and deployment context

The earlier parent used context 256; the current foundation and optimizer arms use context 512. A learned position table with 1,024 entries does not establish that positions 512–1,023 received useful training. The existing dialogue formatter allows 1,024 tokens. Therefore no context-512 continuation may be described as establishing 1,024-token conversational usability.

Before freezing the new pilot, measure tokenized complete-history length distributions on approved prospective teaching and public/development material, including system/role/JSON/tool overhead, without reading private acceptance. Record median, p95, maximum and share exceeding 512. A target sequence includes both history and generated response; a short final answer alone does not make it a short-context task.

The preferred new pilot uses 1,024 positions to remove the known untrained-position gap while adding language exposure. This remains a context-extension experiment: independently packed short documents exercise upper position embeddings but do not teach long-range coherent conversation. Obtain a **separate** bounded hardware preflight on disposable state before choosing this configuration: verify shifted-target arithmetic and source proportions on CPU, then measure actual M4 update time and peak memory under the standard GPU lock/STOP/resource controls, without changing or overlapping current workers. Freeze the preflight's attempted targets, active time, disposable lineage and cleanup policy before it runs; do not train and silently discard unaccounted work. No such preflight is executed by this proposal.

Attention cost and activation memory increase at 1,024 even with equal targets/update; 1,450 targets/s is only a context-512 reference. Replace the duration forecast with measured sustained throughput. If the 1,024 layout cannot fit the resource/time budget, use the explicit 512 pilot and schedule a separately bounded position/context-extension stage before claiming support for full 1,024-token SFT/inference. Do not silently truncate older conversation turns to pass development tests. Freeze additional public/development position-conditioned checks spanning both halves of the table; retain the original short-context diagnostics unchanged. Test the same relevant facts at early and late positions and through longer complete histories, without synthetic padding-only success claims.

## Measurement without a false quality pass

Before the first update and at committed targets **1,007,616; 10,002,432; 20,004,864; 40,001,536; 59,998,208**, evaluate:

- New fixed source-stratified validation: at least 128 distinct held-out documents per source, sampled deterministically before training. Use 32–512 targets wholly within each document, with actual window lengths recorded and padding excluded from loss. Preserve a short-document stratum (32–127 targets) and a longer stratum (128–512); publish counts and eligible-pool coverage. Do not retain only documents long enough for 512 targets. If a stratum is unavailable, disclose it before freezing rather than silently substituting. One window/document avoids treating multiple windows as independent documents.
- Report each source's document-mean CE, summed NLL/actual targets, length-stratum results, matched-document deltas and descriptive paired uncertainty. A single mixed average can hide web regression behind easy narrative gains. Keep original 256 fixed web windows as a distinct transfer series with their unchanged hashes and evaluator.
- Reuse original 32 strict counterfactual context pairs and 32 raw greedy 48-token continuations unchanged. Retain every raw output, prompt identity, decoding configuration and loop flags. Add no penalty, repair, retrieval, canned response or tool substitute to make the base appear better. These checks are narrow diagnostics, not conversation acceptance.

Use the existing deterministic two-consecutive-material-regression confirmation policy separately on new narrative, new web and original web transfer series, with `max(0.20 nats, 5 descriptive paired SE)` as its existing engineering stop threshold. Failure to improve is not automatically numerical divergence. Review at 20M; if metrics are flat or mixed, finish only within the frozen cap unless an actual stop criterion fires, then report the uncertainty rather than claim a curriculum win. Any discretionary early stop is recorded and cannot be followed by undisclosed extra attempts under this budget.

## Adaptive path to conversation and tools

The pilot ending is a decision point, **not the end of the user's objective**. After endpoint verification, inspect development-only language/context results and raw generations. Do not require an invented absolute CE threshold before testing the interface, and do not infer that lower CE means conversation readiness.

Prepare a separately bounded assistant-only SFT stage using family-disjoint, quality-reviewed short conversations and genuine calculator/unit-tool execution traces. Include clarification, corrected user facts, no-tool turns, tool errors and post-tool answers grounded in observed results. Split by task/template/value families before generation; obtain fresh root custody screening for newly generated teaching data. Do not silently recycle old teaching fixtures as new generalization evidence. Existing Smol dialogues have no function calls and cannot supply tool supervision.

Freeze a small SFT diagnostic and its development metrics before execution. Track complete assistant-frame validity, tool choice, arguments, end-to-end executed result, faithful readback, context correction, no-tool behavior and complete multi-turn success separately. If language appears improved but SFT fails frame emission, test formatting/masking with a bounded overfit diagnostic; if frames are valid but arguments/context fail, improve semantic teaching or base training rather than hide failures with parser repair. If language remains poor, compare further targeted continuation against the separately documented smaller-model candidate using a new explicit budget. No automatic unbounded token extension follows this proposal.

Only a candidate showing development-level conversation and executable-tool usefulness proceeds to root-owned private acceptance under the established custody process. Sealed cases remain closed during preparation/training and are never used for selection or repair. Passing base CE, story fluency or JSON grammar alone cannot promote the model as usable.

- `base_run_control.Campaign`, checkpoint locking/checksum machinery, resource guards, `base_train.precision`, `compare_losses` and `language_diagnostics` are suitable reusable primitives. Keep their frozen files unchanged and pin imported identities.

- `optimizer_ablation_train.verify_parent` accepts only the fixed foundation endpoint; its initializer is deliberately branch-specific. Test each possible selected arm, initial moment/step equality, interrupted replay budgets, cursor reconstruction and tamper refusal on tiny CPU fixtures before freeze.
- Existing `sft.py` is a frozen fixture diagnostic with hardcoded budget/development hashes, an older base-loading route and fresh optimizer initialization. Do not run it unchanged as the new SFT campaign. `dialogue.training_row` already supplies role framing and assistant-target masking; `train.backward_rows` supplies target-normalized accumulation; sequential evaluation mechanics are reusable only with independently specified development data and pinning. A future SFT optimizer reset/continuation choice must be explicit; this language pilot's full-moment requirement must not be silently carried over or silently discarded.
