What is unlikely to be the main fix

  • More repetition penalty: final raw traces contain 212 generations, 209 normal EOS endings, three length endings, zero context overflows; only four exceed 20% repeated four-grams. Mean repeated-four-gram fraction is 1.95%. Low repetition coexists with 3% whole-conversation success. This is descriptive evidence, not a controlled causal test.
  • Just increase 512: longer context matters for the original rolling chat, but it cannot explain this final suite's zero overflow and wrong first-turn answers. Increasing a configuration number does not train long-context behavior. The 96 output cap affected only three final generations.
  • Tokenizer IDs are silently remapped: saved audits found zero changed/missing pretraining IDs and zero rendering mismatches across 4,397 clean episodes. These checks do not prove every numerical operation is correct.
  • One embedding or role-format patch: role reset and readable-role ablations failed. Repeating them is not justified without new evidence.
  • A bigger model immediately: increasing parameters on the same tiny data/compute budget may worsen undertraining. Depth/width changes are secondary until the data and reference implementation pass.
  • Retrieval, DPO or RL as rescue: the local retrieval attempt fell to 0/40; preferences cannot supply missing basic competence. These remain later-stage options, not the next default.

5. Recommended recovery plan

Recommendation: preserve the 200M-parameter cap and propose relaxing random initialization for the practical model. Benchmark SmolLM2-135M-Instruct with its native tokenizer/template before fine-tuning. It is an experimental candidate, not a promised solution. Keep our from-scratch lineage separately. A pretrained comparison is not a claim that our model improved.

If random initialization is non-negotiable, retain that constraint and use Track B below. “Full freedom to suggest changes” is not treated as permission to silently replace the student, spend on cloud compute, resume the expired goal or launch training.

Data changes that directly target the observed mistakes

  • Write full user → call → actual fixture → answer → follow-up trajectories. Include operand order reversals, changed numbers, query/entity copying, missing arguments, no-call requests, unavailable capabilities, fixture errors and corrections.
  • Use counterfactual pairs: same wording with a different number/entity/date; same entities with a different requested operation. The answer must change when the relevant fact changes and remain stable under harmless paraphrase.
  • Train concise direct answers plus natural variations. Deduplicate prompts, answers and task templates; cap exact canned-response exposure. No source dominates simply because its responses are short. Track unique scenarios, assistant targets and repeated presentations separately.
  • Use a deterministic oracle for arithmetic, dates, copying and executable fixtures; use actual-history-aware rubrics for subjective conversation. Separate author and reviewer passes, resolve disagreements, and label both as assistant review. Manually review a stratified sample before admitting a new source; any critical error quarantines the batch pending repair.
  • After the student has basic competence, collect its mistakes on a development-only correction pool and obtain short corrected replies. Never create training examples from the new sealed test. This is sequence-level teacher supervision; white-box KL distillation is a different project.
  • Do not mix later NCERT/IIT/NEET, computer-science and Defender specializations into this recovery. Keep a shared competent chat/tool base first. Future domain forks need separate content-grounding and safety gates; adding these domains now expands an already unsolved problem.

Runtime and tool changes

Prefer a maintained local runtime with native checkpoint/template support ([15] MLX LM), verified against a stock reference. Keep the custom trainer as a research path until numerical parity is established. Start new-model evaluation at its supported context length; do not reinterpret the existing model as long-context without training. Cache past attention states for speed only after output-parity tests.

Use schema-constrained decoding for tool-call regions if the local adapter is verified, then validate allowed tools, argument types and permission. Report wrong-but-valid calls separately. Keep prose decoding independent; test only a small prespecified decoding comparison on development. Optional deterministic fixture-result rendering can prevent result corruption in the application, but it must be labeled application assistance and must never count as improved raw-model conversation accuracy.

Track B: preserve from-scratch training

  1. Pass the same runtime/evaluation checks. Under a separately authorized diagnostic, a tiny training-set fit test should reproduce ≥95% of 64 simple training answers; failure blocks scaling and triggers implementation/objective debugging. This is not a generalization score.
  2. Benchmark both preserved foundations on fresh language/grounding diagnostics. Choose continuation versus a fresh initialization based on this evidence; do not restart just to obtain a cleaner project label.
  3. Prepare a deduplicated, source-licensed 0.5B-token first tranche, then a 2B total-token ceiling for the initial research phase. Use an initial proposed mix such as 50% curated educational prose, 25% simple explanations/narratives, 15% grounded QA/document tasks, 10% coherent conversational text; audit and adjust using development evidence, not confirmation. Preserve original domains to detect forgetting. [14] FineWeb-Edu
  4. Evaluate fixed language-loss sets and identical small conversation probes at 0.5B and 1B milestones. If language loss improves but the same controlled SFT probe produces no clear conversation gain, stop before 2B. Extend toward 5B only with repeatable improvement and new approval; no claim that any token count guarantees 60%.
  5. Use one coherent curriculum and a sustained training run, not many tiny branches. Maintain separate counters for pretraining, dialogue-context and assistant targets. Architecture changes require one matched pilot; do not combine a larger model, new tokenizer, new optimizer and new data in one unidentifiable experiment.

8. Research and evidence index

Primary author/model/dataset/framework sources inspected on 3 November 2026. Findings are summarized with limits; no external benchmark is substituted for local conversation accuracy.

  1. SmolLM training report — 135M and 360M models trained on 600B tokens; data curation is central. Published budgets are reference points, not minimum requirements for this task.
  2. SmolLM2-135M-Instruct model card — 135M, 2T pretraining tokens, Apache-2.0. Function-calling claim applies to 1.7B, not this size. No evidence it reaches our 60/100 conversation gate.
  3. Smol-SmolTalk dataset card — Shorter conversations for models below 1B; deliberately excludes function calling and advanced math. Useful chat source, not a complete tool curriculum.
  4. MobileLLM-125M model card — 125M and 1T training tokens; deep/thin design, shared embeddings and GQA. Research license and integration differences make this a design reference, not the first deployment choice.
  5. TinyStories — Small models can learn coherent constrained-domain stories. This does not establish general conversation or tool competence.
  6. Compute-optimal training / Chinchilla — Model size and training data must be considered together. Compute-optimal language loss does not imply a guaranteed chat threshold.
  7. LIMA — The 1,000-example alignment result starts with an already pretrained 65B model. It is not evidence that a weak 97.5M foundation can learn general language from 1,000 examples.
  8. APIGen — Separates format checking, actual execution and semantic verification. Its published performance does not transfer automatically to a 100M model.
  9. APIGen-MT — Uses verified task blueprints and complete multi-turn trajectories. Adopt the data-verification principle, not its larger-model benchmark numbers.
  10. MiniLLM — Distillation uses an on-policy objective and teacher distribution access. Text-only Codex-generated corrections are sequence supervision, not this white-box distillation method.
  11. Neural text degeneration — Decoding can cause repetitive text; sampling changes generation behavior without establishing factual correctness.
  12. Unlikelihood training — A training objective can suppress undesirable repetition. It is a secondary option after competence, not a substitute for grounding.
  13. XGrammar quick start — Grammar constraints can enforce JSON/schema structure. Correct syntax does not choose the right operation, arguments, permission or answer; local integration remains to be tested.
  14. FineWeb-Edu — Educational filtering offers a candidate source for foundation data. It is not individually verified truth or a substitute for source audits and deduplication.
  15. MLX LM — Apple-silicon inference and fine-tuning support. Verify the chosen architecture, native template and numerical parity before adopting it.
  16. nanowhale-100m model card — Author reports ~110M total parameters, 2.6B pretraining tokens and 72.7M SFT tokens over 460K conversations. Held-out token accuracy is not conversation accuracy. Custom architecture increases integration risk.
  17. nanochat reference implementation — Inspectable end-to-end training and chat pipeline. Its accelerator cost/speed claims are not laptop ETAs or proof of performance under our parameter cap.
  18. FunctionGemma — Specialized 270M tool model. It exceeds the current 200M cap and is only a possible future option if that cap changes.
